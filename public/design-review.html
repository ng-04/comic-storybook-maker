Design review · Phase 1

Design review on paper

The Phase 1 build checked against the agreed user journey and constraints. It follows one request from the screen to the finished book, then works through four failure cases.

Nothing on this page has been run. Every behaviour below comes from reading the code at commit f68a362 (source). Paper tests are predictions, not test results. Costs use Google's published price for gemini-2.5-flash-image, about US$0.039 (≈ ₹3.3) per image; check the Google Cloud billing page for the real figure.

1. What it is checked against

  • Journeys: J1–J7 in docs/goal-spec.md, plus Simple mode (form → Check the words → draw), which was added later.
  • Principles: review before spend, child-safe by default, private by default, honest about AI.
  • Phase 1 constraints:
    • Static site on GitHub Pages, with each visitor's browser calling Claude and Gemini directly.
    • Keys come from the passkey file keys.enc.json or Settings, and are never in the bundle.
    • Demo mode needs no keys.
  • Agreed in the last design review:
    • A daily limit of about ₹100.
    • The owner restricts the Gemini key in Google Cloud Console.
    • Two tabs open on the same book are out of scope.
  • Phase 2 (AWS) is a plan, not code. When an answer depends on Phase 2, it says so.

Where Advanced mode differs

  • Character sheets. Before step 4, each character's sheet is drawn and then approved. Each sheet is billed, and the character's reference photos go to Google.
    • The approved sheet then becomes the reference image for every page that character is on.
  • Outline review. Step 6 is the Outline screen, which adds "Rewrite this page". Each rewrite is billed by Anthropic.
  • Grid pages. A grid page is 6 images, so a 12-page grid book is 62 images, about ₹205.

No share link is built in Phase 1. J5 counts as done once a PDF is downloaded, as goal-spec allows.

4. Four paper tests

Each test describes what the user would see and which part of the code is responsible. None of these has been run.

A. The image service is slow

Gemini takes several minutes to answer, or never answers.

  • What the user sees:
    • Pages stay on "Drawing…" with no time limit.
    • Other pages stay "Queued", and Redraw in the page editor waits silently.
    • There is no Stop button for drawing.
    • Reloading the page is the only way out. Afterwards, opening the Pictures screen starts the same pages drawing again, and those requests are billed.
  • Who is responsible: nothing enforces a time limit.
    • requestOnce (gemini.ts:66) has no timeout.
    • slot() (gemini.ts:28) holds its 3 places for as long as a request is open.
    • The only abort signals come from a new outline (writeOutline → stopIllustrating) and from deleting the book.
  • Claude being slow: this case behaves better.
    • The Writing screen shows the time taken, and its progress bar stops at 96%.
    • Cancel works, because cancelWriting aborts the stream.
    • There is no time limit of our own, though: the SDK's default timeout applies, with 2 retries (claude.ts:18).
  • What the spec requires: backend-spec §5 limits a page image to 90 s and a story to 120 s.
  • Phase 2: the worker Lambda timeout would enforce these limits, and job polling would show "failed" when one runs out.

B. The model returns a valid but wrong answer

Examples:

  • Claude returns 8 well-formed pages, but the hero has the wrong name, the ending has no "Seekh:", or a caption is 600 characters.
  • Gemini returns a picture with writing in it, the wrong child, or a scary scene.
  • What the user sees: the story appears on the Check screen (Simple) or the Outline screen (Advanced), and looks normal.
    • A wrong picture shows as Done.
    • A long caption overflows the page panel.
    • On a grid page, a panel whose speaker doesn't exist quietly loses its speaker, because toPanels sets it to '' (direct.ts).
  • Who is responsible:
    • The person is the only content check. That is the Check or Outline screen before drawing, and Redraw or "pick a version" after.
    • The JSON schema guarantees the shape of Claude's reply, not what it means.
    • The code only checks the page count, and the panel count on grid pages (direct.ts:41, :82).
  • What the spec requires: backend-spec §4.3 asks for length checks, a check that each speaker exists, and an output safety check (keyword list plus an LLM classifier). None of these is built.
  • Pictures: nothing checks the images at all.

C. An old reply arrives after the user has corrected something

  • Case C1, a page redraw. In the page editor the user presses Redraw, then corrects the prompt while it is still drawing. The prompt box stays editable during drawing (PageEditor.tsx:99).
    • The picture drawn from the old prompt arrives. It is added as a new version and made the active one.
    • The box shows the new prompt and the picture matches the old one, and nothing on screen says so.
    • drawPage drew from a copy of the story taken at the start (store.ts:482). The version doesn't record which prompt it was drawn from, although backend-spec asks for promptSnapshot.
    • Nothing prevents this.
  • Case C2, the story. While "Writing your story…" is showing, the user goes back to the form and fixes the hero's name. The Writing screen says they can look at other steps meanwhile.
    • The story written from the old form arrives, replaces the pages, and opens the Check screen with the old name.
    • The Check screen is the only safeguard, because the person might notice. Nothing compares the form to what was sent.
  • Case C3, a new draft or a deleted page. This one is safe.
    • The new outline gets new page IDs, so a late updatePage for an old page finds nothing and does nothing.
    • Rewrite locks that page's text boxes while it runs (Outline.tsx).
    • The one side effect: an image file that arrives late stays in IndexedDB with nothing using it.
  • Case C4, Simple mode cover. If the cover is redrawn while other pages are still drawing, those pages keep the old cover as their style reference.
  • Phase 2: the plan's If-Match: revision catches conflicting saves of the story. It does not catch C1, because a job result isn't a save from the browser. That needs the change proposed in gap G6 below.

D. A save succeeds but its reply is lost

  • Case D1, Google draws the picture but the reply never arrives. The connection drops after Google has started generating, and Google bills for the picture.
    • fetch fails, which counts as OFFLINE and can be retried, so the same step is tried up to 3 times. Every attempt that reaches Google is billed again.
    • If all 3 attempts fail, drawPage marks the page queued with no error (store.ts:497), and finally → pump starts it again straight away.
    • The browser still says it is online (navigator.onLine), so this repeats with no limit for as long as Google can't be reached.
    • What the user sees: the page keeps flipping between "Drawing" and "Queued". Nothing says it is spending.
    • Nothing limits it.
  • Case D2, Claude writes the story but the reply is lost. The SDK resends the request up to 2 more times (claude.ts:18), and each one is billed.
    • Then the user sees "Couldn't reach Anthropic" with a Try again button.
  • Case D3, a local save is lost.
    • The picture is saved to IndexedDB, but the story record that points to it is only written up to 400 ms later.
    • If the tab closes in that gap, the picture is lost. The file is still stored, but nothing points to it.
    • revive then puts the page back to queued, and opening the Pictures screen pays for it again.
  • Who should prevent it: in Phase 1, no component does.
    • Phase 2 plans Idempotency-Key on POST requests and workers that do each jobId only once (backend-spec §5).
    • That stops our repeats. It cannot stop Google billing for a reply that was lost, because the Gemini API has no idempotency key.

5. What could be removed

There are no agents in this design. Every model call is a single request: one story, one rewrite, one image. So there are no agents to remove. These parts can go without breaking a requirement:

  • v1 key import (V1_KEYS, settings.ts:32).
    • No requirement needs it now that the passkey and Settings exist.
    • It copies keys from another app on the same origin, which spreads them further (see gap G4).
    • Acceptance: with only the comic* v1 keys in localStorage, the first visit opens Unlock or Settings, not the library.
  • Simple-mode rewrite. This is simpleRewritePrompt and the Simple branch of rewritePage (direct.ts:111).
    • No Simple screen can reach it, because the step bar has no Outline step for Simple books.
  • The Claude server-side fallback (fallbacks: 'default', claude.ts:57).
    • No requirement asks for it.
    • When a request is refused, it quietly moves the story to another model. That works against "honest about AI" and against a cost you can predict.
    • Without it, a refusal shows "Claude declined to write this story", which the app already handles.
  • Phase 2: SQS. The spec keeps the queue only to get past API Gateway's 29 s limit. An asynchronous Lambda call (InvocationType: Event) with an on-failure destination still gives a 202 with a job ID, retries and a dead-letter place.
    • That is one fewer service. CLAUDE.md says to confirm the architecture before building, so this is a proposal.

Looked at and kept

  • The two concurrency limits. These are PAGE_CONCURRENCY in the store and slot() in gemini.ts.
    • The store limits how many pages show "Drawing".
    • slot() limits requests overall, which grid pages (6 each) and sheets need.
  • jsPDF and html-to-image. The browser's Print could replace them, but "Save as PDF" in a print dialog is hard for grandparents, especially on phones.
  • Mock or demo mode. goal-spec requires it.
  • Version history. J4 requires it.

Doc drift: the comment at the top of src/pdf/exportPdf.ts says "Phase 2 renders server-side". backend-spec §4.6 says the PDF is never made on the server.

6. Claimed but not enforced

Each gap is a boundary for isolation, cost or permission that the spec or an earlier decision promises, but the code doesn't yet enforce. For each one there is a proposed change to the spec and a test you can watch pass or fail. All of these are proposals; none is built.

G1 · cost The ₹100-a-day limit

Claimed
Agreed in the last design review.
Actually
No code counts spending.
  • An 8-page grid book in Advanced mode is 38 images (≈ ₹126), and a 12-page one is 62 (≈ ₹205). Either one goes over the limit before any retries.
  • A shared passkey means every browser that unlocks it spends on the same accounts.
Spec change
Add a per-browser spend log in localStorage, kept by day.
  • Before every billed request, gemini.ts and claude.ts add an estimate to the log (image ₹3.5; story at its token estimate). If that would pass the limit, they refuse with QUOTA_EXCEEDED without sending anything.
  • When the limit is reached (decision D1: draw until the limit, then pause):
    • Requests already sent are allowed to finish, because they're already paid for.
    • Queued pages get a new status, paused, shown as "Paused until tomorrow". The book stays readable with the pages already drawn.
    • Redraw, Retry and Draw sheet are disabled, with the same message.
    • When the day changes (local midnight), paused pages go back to queued. Whether they then draw on their own or after a click is decision D3.
    • revive keeps paused as it is when the tab is reopened.
  • "Draw the pictures" shows the estimated cost and today's remaining amount, for information only. It doesn't block.
  • The hard limit for everyone together is set outside the app: an Anthropic workspace spend limit, and a requests-per-day quota on the Gemini API in Google Cloud.
Acceptance
  • With today's log at ₹98, pressing Redraw shows "Today's limit is reached" and the network panel shows no request to generativelanguage.googleapis.com.
  • With the log at ₹93 and pictures counted at ₹3.5, starting an 8-page Simple book sends exactly 2 picture requests. The other 6 pages show "Paused until tomorrow", and no more requests go out.
  • Moving the clock past midnight puts those 6 pages back to queued.

G2 · cost Retries have no limit

Claimed
"Max image retries per job = 3 transient + 3 ladder steps" (backend-spec §5).
Actually
Each image does stop at 9 requests, but the OFFLINE → queued → pump loop starts the page again with no limit (test D1).
Spec change
  • Keep a per-page count of attempts in memory. After 2 full rounds that ended OFFLINE, mark the page failed with "Couldn't reach Google's image service", even if navigator.onLine says online.
  • Set Claude's maxRetries to 0 for story writing, so a repeat only happens when the user presses Try again, and every repeat counts toward G1.
Acceptance
In a test where every fetch to Google throws while the browser reports online, one page sends at most 6 requests (2 rounds of 3) and then shows Failed.

G3 · cost Time limits

Claimed
Page images 90 s, sheets 90 s and stories 120 s (backend-spec §5).
Actually
No time limit on Gemini. Claude uses the SDK default (test A).
Spec change
  • requestOnce combines the caller's signal with AbortSignal.timeout(90_000). Running out of time counts as a transient error, so it is retried and then fails.
  • claudeJson passes timeout: 120_000.
  • The Pictures screen gets a Stop drawing button that calls stopIllustrating and puts queued pages back to "Not drawn".
Acceptance
With a fake Gemini that never answers, the page shows Failed with "took too long" after the retries. A Redraw on another page starts within 1 s, because its place in the queue has been freed.

G4 · isolation Keys and children's photos are shared with every site at ng-04.github.io

Claimed
"Private by default". settings.ts says the keys are "sent only to Anthropic and Google".
Actually
Every GitHub Pages site under ng-04.github.io/* is the same origin. That includes v1 at /comic, the homepage and every future repo.
  • Any script on any of those pages can read localStorage['csm2-settings'], which holds the plain keys, and the IndexedDB photos.
  • There is no Content-Security-Policy, so nothing limits where code on this page can send them.
Spec change
  • Serve the app from its own origin: a custom subdomain such as comics.<your-domain>, or Phase 2 on CloudFront.
  • Add a CSP <meta> tag with connect-src 'self' https://api.anthropic.com https://generativelanguage.googleapis.com.
  • Drop the v1 key import.
Acceptance
  • A test page at ng-04.github.io/anything/ reads localStorage.getItem('csm2-settings') and gets null.
  • On the app, fetch('https://example.com') in the console is blocked by CSP.

G5 · permission Review before spend is only enforced by buttons

Claimed
  • "Zero page-image jobs before Draw the pictures".
  • "Every character sheet approved", otherwise 422 SHEETS_NOT_APPROVED.
Actually
  • The only check is the disabled button on the Outline screen (Outline.tsx:145).
  • startIllustrating and drawPage don't check anything themselves. A page opened directly in the page editor can be drawn before approval.
  • Opening the Pictures screen, or coming back online, also spends without a click.
Spec change
  • drawPage refuses unless story.status is illustrating or done and pendingSheets(st) is empty.
  • startIllustrating checks the same.
  • Whether to resume on its own is decision D3.
Acceptance
A unit test calls drawPage on an outline story that has an unapproved sheet. The Gemini mock gets zero calls and the page status doesn't change.

G6 · correctness Old replies win

Claimed
PageVersion.promptSnapshot (backend-spec §2). Also "no lost edits".
Actually
Neither is in the code (test C1, C2).
Spec change
  • Each request records a fingerprint of what it was made from. For a page that is the prompt and panels; for a story it is the form or setup.
  • Each version stores the prompt it was drawn from.
  • If a reply arrives and the fingerprint no longer matches, a picture is saved as a version but not made active, and a story is shown with "Your story idea changed while this was being written", so the user can either write it again or keep it. Decision D4 is about this.
Acceptance
Start a redraw with a mock that takes 2 s, change the prompt after 1 s, and wait. The active version stays the same, a new version appears with "drawn from your earlier prompt", and that version stores the old prompt.

G7 · safety Nothing checks what the story says

Claimed
"Child-safe by default". Validate lengths and speakers, and run an output safety check (backend-spec §4.3).
Actually
Only the shape of the reply and the page and panel counts are checked (test B).
Spec change
  • Add a free check, validateOutline, in direct.ts. It checks:
    • captions are 400 characters or fewer, and bubbles 90 or fewer;
    • the hero's name appears on the cover and at least half the pages;
    • the last page starts "Seekh:";
    • every image prompt ends "No text, letters or speech bubbles.";
    • every speaker exists;
    • no word from a short blocked list appears.
  • If the check fails, retry once, then fail with GENERATION_INVALID.
  • Whether to also pay for a classifier is decision D7.
Acceptance
A mock returns an ending without "Seekh:". The app sends exactly 2 requests and then shows "The story came back incomplete", and no page is replaced.

G8 · cost A local save in two steps can pay twice

Claimed
"No lost edits".
Actually
The image is saved immediately, but the record that points to it is saved up to 400 ms later (test D3).
Spec change
When a version is added, drawPage and drawSheet write the story to IndexedDB immediately, not on the 400 ms timer. The same goes for any change of status.
Acceptance
With fake-indexeddb, once drawPage has finished, db.listStories() already shows the new version without moving the clock on.

G9 · permission Unlocked keys can do anything the account can

Claimed
The owner restricts the Gemini key, as agreed.
Actually
Nothing checks whether that was done.
  • The Anthropic key can do anything its workspace can.
  • A referrer restriction only stops casual misuse in browsers. Anyone outside a browser can fake the referrer.
Spec change
  • Add an owner checklist in Settings.
    • The Gemini key is limited to the Generative Language API and the https://ng-04.github.io/* referrer, or the new origin from G4.
    • The Anthropic key sits in its own workspace with a monthly spend limit.
  • Rotate both keys whenever someone who knew the passkey should lose access.
  • Phase 2 removes this gap, because the keys move to Secrets Manager.
Acceptance
  • A curl to the Gemini model endpoint with the key and no referrer returns 403.
  • The Anthropic Console shows a spend limit on that key's workspace.

7. A correction to the understanding check

The answer key for question 6 says that the online listener is the only way to spend without a click. That is incomplete: opening the Pictures screen also starts any queued pages (Illustrate.tsx:21, useEffect → pump). That includes reopening the tab on that screen after revive has put pages back in the queue.

8. Open product decision

Decisions are taken one at a time. Each answer changes the spec above before the next question is asked.

D1, decided: draw until the limit, then pause. Pages that don't fit in today's ₹100 show "Paused until tomorrow" and continue the next day. G1 above has been updated to match.

D2 of 7: Is the ₹100 per browser, or one limit for everyone who has the passkey?

In Phase 1 the app can only count what this browser spends. If 4 family members unlock with the passkey, they can spend ₹400 a day between them on the same accounts.

  • A. Per browser in the app, plus a hard total set at the providers (recommended).
    • The app pauses each browser at ₹100, as in D1.
    • You also set a hard ceiling for everyone together, outside the app: a requests-per-day quota on the Gemini API in Google Cloud Console (about 30 pictures a day ≈ ₹100), and a monthly spend limit on the Anthropic workspace.
    • If the provider ceiling is hit first, those pages fail with "the image service's daily limit is reached", and the app treats that like the pause.
  • B. Per browser only. Simplest. The total is ₹100 × the number of people using the passkey.
  • C. One shared total, counted by the app. This needs a server that every browser reports to, which means bringing part of Phase 2 forward.
Next, once D2 is decided:
  • D3: resume drawing on its own, or after a click;
  • D4: what to do with an out-of-date reply;
  • D5: its own domain, or stay on ng-04.github.io;
  • D6: children's photos and the Gemini paid tier, plus the consent wording;
  • D7: a paid safety classifier, or free rules only.
